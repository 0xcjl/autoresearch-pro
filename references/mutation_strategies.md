# Mutation strategies

Read only when choosing a bounded edit is difficult. Start from a concrete failure
or a testable hypothesis; keep the target's capability and authority unchanged.

| Observed problem | Small edit | Useful comparison |
|---|---|---|
| Adjacent requests load the skill | Narrow description to task intent and exclusions | Normal and adjacent routing cases |
| A necessary action is missed | Clarify the step's input, action, and observable result | Run the failing case again |
| Rules conflict or repeat | Merge into one decision rule at the original location | Check both affected cases |
| Agent asks despite clear scope | Make the question conditional on a material unknown | Clear and ambiguous requests |
| Outputs claim unsupported certainty | Require source evidence or an explicit unknown | Missing-evidence case |
| A workflow is costly or overlong | Remove a step that does not change the outcome | Compare actual outputs and steps |

Make related edits as one hypothesis, not a collection of unrelated improvements.
An example is useful only if it teaches a transferable decision; do not hardcode
the test's answer. Tighten actions and conditions, never replace “might” with “is”
unless evidence establishes the fact. Keep the evaluation inputs and acceptance
criteria fixed. Inconclusive comparisons go back to the original, not to more rules.
